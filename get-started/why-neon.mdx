Neon is a fully managed, serverless Postgres platform built from the ground up for modern application development. It runs standard Postgres — fully compatible with every driver, ORM, and extension you already use — but it's designed differently from traditional managed Postgres, in ways that change how you build, test, and scale.

## What "serverless Postgres" actually means

Traditional managed Postgres runs on a provisioned virtual machine. You pick an instance size, pay for it whether or not your app is busy, and plan for peak capacity in advance. Scaling means moving to a bigger VM, often with downtime.

Neon takes a different approach. Its architecture decouples storage and compute entirely:

- **Storage is distributed, durable, and versioned** — data lives in cloud object storage, replicated across availability zones, and retains a full history of changes.
- **Compute is stateless and ephemeral** — compute processes attach to that storage when queries arrive and can be started, stopped, or resized at any time without touching the data.

This separation is not a product layer on top of Postgres — it's the foundation. It's what makes autoscaling, scale-to-zero, instant branching, and instant restores possible without adding operational complexity.

## Developer experience

Neon's architecture enables a set of features that change how development teams work day-to-day.

### Branching for development, previews, and testing

Instead of sharing a single staging database or managing separate instances, teams use Neon branches as isolated, disposable environments:

- **Branch per developer** — each engineer works against their own isolated database, avoiding schema conflicts and shared state.
- **Branch per pull request** — preview deployments get production-like data automatically, without manual setup.
- **Branch per CI run** — test suites start from a clean, known state every time.
- **Branch reset** — reset a branch to match its parent with a single command whenever you need a fresh start.

### Standard Postgres compatibility

Neon is not "Postgres-like." It is Postgres. You can connect with any driver, use any ORM, enable standard extensions, and run existing migrations without changes. If it works with Postgres, it works with Neon.

### API-first and automation-ready

Every operation in Neon — creating projects, branches, and databases; managing roles; resetting branches; reading connection strings — is available through the [Neon API](https://api-docs.neon.tech) and [Neon CLI](/reference/neon-cli). Teams can automate database lifecycle management the same way they automate code deployments.

## Who uses Neon

### Individual developers and side projects

Neon's Free Plan is designed to be useful, not just available. It includes up to 100 projects, 0.5 GB of storage per project, and compute that scales to zero when idle so you don't burn through limits on inactive projects. You get a connection string in seconds and can start building without configuring infrastructure.

### Startups shipping fast

Small teams need to move quickly without getting tangled in database operations. Neon's autoscaling handles unpredictable traffic, branching replaces manual staging environment setup, and instant restores lower the stakes when something goes wrong. The [Neon API](/reference/api-reference) makes it straightforward to automate most database operations.

### Platforms and AI agents at scale

Platforms that provision databases on behalf of users — developer tools, codegen platforms, multi-tenant SaaS products — need a database that can be provisioned in milliseconds, scaled to zero when idle, and managed entirely through an API. Neon powers platforms like Replit that deploy thousands of databases per day. Scale-to-zero makes per-app databases economically viable even at high volume.

## The architecture behind it

At the highest level, Neon treats the object store as the system of record. WAL records and page versions are written directly to durable object storage, not to local disk. The consequences:

- Durability no longer depends on a single machine or attached disk.
- Storage scales independently, effectively without limits.
- Recovery is a metadata operation, not a data copy.
- The full history of the database is retained natively — not reconstructed from backups.

With history preserved in a versioned storage engine, entire databases can be branched or restored instantly. Computes are stateless processes that attach to storage at a specific point in that history, execute queries, and can be stopped or resized at any time without data loss.
