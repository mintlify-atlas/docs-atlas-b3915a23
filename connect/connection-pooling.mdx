Neon uses [PgBouncer](https://www.pgbouncer.org/) to provide connection pooling, enabling up to 10,000 concurrent client connections regardless of your compute size. Without pooling, the number of connections is limited by your compute's available RAM. With pooling, PgBouncer sits between your application and Postgres, reusing a small pool of actual Postgres connections to serve many more clients.

## Why connection pooling matters

Every Postgres connection spawns a new OS process and consumes memory. Neon sets `max_connections` based on your compute size:

| Compute size (CU) | RAM | max_connections |
|---|---|---|
| 0.25 | 1 GB | 104 |
| 0.50 | 2 GB | 209 |
| 1 | 4 GB | 419 |
| 2 | 8 GB | 839 |
| 4 | 16 GB | 1,678 |
| 8 | 32 GB | 3,357 |
| 9–56 | 36–224 GB | 4,000 (capped) |

<Note>
  Seven connections are reserved for the Neon superuser account. For a 0.25 CU compute, this means 97 connections are available to your application.
</Note>

These limits are easy to exhaust in common patterns:

- Serverless functions that open a connection per invocation
- Web frameworks that create a connection per request
- Multiple application instances without a shared connection pool
- Applications that don't close connections cleanly

## How Neon's PgBouncer works

PgBouncer accepts up to 10,000 client connections and routes them through a smaller pool of actual Postgres connections. It creates a separate pool for each combination of database user and database name.

For example, on a 1 CU compute:

- `max_connections` = 419
- `default_pool_size` = 377 (90% of `max_connections`)

This means `user1` can hold up to 377 concurrent active transactions against `database1`, and `user2` can simultaneously hold up to 377 against the same database. All pools share the underlying `max_connections` ceiling.

<Warning>
  The 10,000 limit is for client connections to PgBouncer — not for simultaneous query results. The number of queries that can execute in parallel is still limited by `default_pool_size` and `max_connections`.
</Warning>

## Neon's PgBouncer configuration

```ini
[pgbouncer]
pool_mode            = transaction
max_client_conn      = 10000
default_pool_size    = 0.9 * max_connections
max_prepared_statements = 1000
query_wait_timeout   = 120
```

- **`pool_mode=transaction`**: Connections return to the pool after each transaction completes.
- **`max_client_conn=10000`**: Maximum clients PgBouncer will accept.
- **`default_pool_size`**: Maximum active Postgres connections per user per database (90% of `max_connections`).
- **`max_prepared_statements=1000`**: Maximum protocol-level prepared statements per connection.
- **`query_wait_timeout=120`**: A query that waits more than 120 seconds for a pool connection is rejected.

These settings are managed by Neon and are not user-configurable.

## Pooled vs. direct connection strings

To use connection pooling, add `-pooler` to the endpoint ID in your hostname.

**Direct connection (no pooling):**

```text shouldWrap
postgresql://user1:AbC123dEf@ep-cool-darkness-123456.us-east-2.aws.neon.tech/dbname?sslmode=require
```

**Pooled connection:**

```text shouldWrap
postgresql://user1:AbC123dEf@ep-cool-darkness-123456-pooler.us-east-2.aws.neon.tech/dbname?sslmode=require
```

The Neon Console provides a pooled connection string by default. To get a direct connection string, open the **Connect** modal on your **Project Dashboard** and disable the **Connection pooling** toggle.

### When to use each connection type

| Use case | Connection type | Reason |
|---|---|---|
| Serverless functions | Pooled | Many short-lived connections |
| Web applications | Pooled | Multiple concurrent requests |
| Connection-per-request frameworks | Pooled | High connection churn |
| Schema migrations | Direct | Tools may not support transaction pooling |
| Long-running analytics queries | Direct | Avoid pool contention |
| `pg_dump` / `pg_restore` | Direct | Uses `SET` statements |
| Logical replication | Direct | Requires a persistent connection |
| Admin tasks | Direct | May need session-level features |

## Transaction mode limitations

Because Neon runs PgBouncer in `transaction` mode, connections return to the pool after every transaction. This means session-level Postgres features are not supported over a pooled connection:

- `SET` / `RESET` session variables
- `LISTEN` / `NOTIFY`
- `WITH HOLD CURSOR`
- SQL-level `PREPARE` / `DEALLOCATE`
- Temporary tables with `PRESERVE` / `DELETE ROWS`
- Session-level advisory locks

### The `SET search_path` problem

The most common issue is `SET search_path`, which resets when the connection returns to the pool:

```sql
SET search_path TO myschema;
SELECT * FROM mytable;  -- works
-- transaction ends, connection returns to pool
SELECT * FROM mytable;  -- ERROR: relation "mytable" does not exist
```

To fix this, set the `search_path` at the role level instead:

```sql
ALTER ROLE user1 SET search_path TO myschema, public;
```

Or use schema-qualified names in your queries: `SELECT * FROM myschema.mytable`.

## Protocol-level prepared statements

SQL-level `PREPARE` and `EXECUTE` are not supported with PgBouncer. However, protocol-level prepared statements (sent through your driver's native API) are supported as of PgBouncer 1.22.0.

<CodeGroup>

```javascript node-postgres
const query = {
  name: 'fetch-user',
  text: 'SELECT * FROM users WHERE username = $1',
  values: ['alice'],
};
await client.query(query);
```

```python psycopg2
cur = conn.cursor()
cur.execute(
  'SELECT * FROM users WHERE username = %s;',
  ('alice',),
  prepare=True
)
results = cur.fetchall()
```

</CodeGroup>

## Monitoring connection pool activity

The [Monitoring page](https://console.neon.tech) in the Neon Console provides two graphs for tracking pool activity:

- **Pooler client connections**: Shows active, idle, and waiting client connections to PgBouncer.
- **Pooler server connections**: Shows active and idle Postgres connections from PgBouncer.

PgBouncer metrics are also available via OpenTelemetry and Datadog integrations.

## What happens when you hit limits

<AccordionGroup>
  <Accordion title="Per-user-per-database pool limit (query_wait_timeout)">
    When all connections in a user's pool are busy, new queries wait in a queue. After 120 seconds without a free connection, the query fails with:

    ```
    query_wait_timeout
    ```

    **Solutions:** Ensure transactions complete quickly, use a larger compute, or use multiple database users to create additional pools.
  </Accordion>
  <Accordion title="Global client connection limit (max_client_conn)">
    When 10,001 clients attempt to connect to PgBouncer:

    ```
    no more connections allowed (max_client_conn)
    ```

    **Solutions:** Fix connection leaks, implement client-side connection pooling, or reduce the number of application instances.
  </Accordion>
  <Accordion title="Direct connection limit (max_connections)">
    When using a non-pooled connection string on a small compute:

    ```
    FATAL: remaining connection slots are reserved
    ```

    **Solutions:** Switch to a pooled connection string, increase compute size, or add application-level pooling.
  </Accordion>
</AccordionGroup>
