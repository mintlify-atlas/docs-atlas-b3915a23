---

Terraform lets you define cloud infrastructure in declarative configuration files and apply changes consistently and repeatably. Neon sponsors a community-maintained Terraform provider so you can manage your Neon projects, branches, databases, and endpoints the same way you manage the rest of your infrastructure.

The provider is maintained by Dmitry Kisler and published on the [Terraform Registry](https://registry.terraform.io/providers/kislerdm/neon/latest). Source is on [GitHub](https://github.com/kislerdm/terraform-provider-neon).

<Warning>
  This provider is community-maintained, not officially supported by Neon. Review the provider's changelog before upgrading, and open issues on the [provider's GitHub repository](https://github.com/kislerdm/terraform-provider-neon) if you encounter problems.
</Warning>

## Prerequisites

- Terraform CLI `1.14.x` or later — [install from HashiCorp](https://developer.hashicorp.com/terraform/install)
- A Neon account — [sign up](https://console.neon.tech/signup) if you don't have one
- A Neon API key — create one in **Account settings** > **API keys**

## Set up the provider

<Steps>
  <Step title="Create a project directory">
    ```bash
    mkdir neon-terraform-project
    ```
  </Step>

  <Step title="Declare the provider in main.tf">
    ```hcl
    terraform {
      required_providers {
        neon = {
          source = "kislerdm/neon"
        }
      }
    }

    provider "neon" {}
    ```
  </Step>

  <Step title="Set your API key">
    The provider reads the `NEON_API_KEY` environment variable automatically:

    ```bash
    export NEON_API_KEY="your-api-key-here"
    ```

    Alternatively, you can pass the key directly in the provider block — but avoid this in shared configurations or version control:

    ```hcl
    provider "neon" {
      api_key = "your-api-key-here"
    }
    ```
  </Step>

  <Step title="Initialize Terraform">
    ```bash
    terraform init
    ```

    This downloads and installs the Neon provider plugin.
  </Step>
</Steps>

<Note>
  Avoid `terraform init -upgrade` in CI pipelines and auto-approved pull requests. Provider schema changes can trigger unintended resource replacements. Run upgrades manually and review the plan output before applying.
</Note>

## Core resources

### neon_project

A project is the top-level container for all Neon resources.

```hcl
resource "neon_project" "my_app_project" {
  name       = "my-application-project"
  pg_version = 16
  region_id  = "aws-us-east-1"
  org_id     = "your-neon-organization-id"

  history_retention_seconds = 21600

  branch {
    name          = "production"
    database_name = "app_db"
    role_name     = "app_admin"
  }

  default_endpoint_settings {
    autoscaling_limit_min_cu = 0.25
    autoscaling_limit_max_cu = 1.0
  }
}
```

<Warning>
  Always set `org_id` when creating a `neon_project`. Omitting it can create resources in the wrong organization or produce duplicate projects, and subsequent `terraform plan` runs may attempt destructive changes including deletions. Find your Organization ID in the Neon Console under **Account settings** > **Organization settings**.
</Warning>

Key attributes:

| Attribute | Required | Description |
|---|---|---|
| `name` | No | Project name |
| `pg_version` | No | Major PostgreSQL version (e.g., `17`) |
| `region_id` | No | Cloud region (e.g., `aws-us-east-1`) |
| `org_id` | **Yes** | Organization ID — always set this explicitly |
| `history_retention_seconds` | No | Point-in-time recovery window. Free plans max at 21600 (6 hours) |

Output computed values for use in other resources:

```hcl
output "project_id" {
  value = neon_project.my_app_project.id
}

output "project_connection_uri" {
  value     = neon_project.my_app_project.connection_uri
  sensitive = true
}
```

### neon_branch

Branches are copy-on-write clones of a parent branch.

```hcl
resource "neon_branch" "dev_branch" {
  project_id = neon_project.my_app_project.id
  name       = "feature-x-development"
  parent_id  = neon_project.my_app_project.default_branch_id
}
```

Key attributes:

| Attribute | Required | Description |
|---|---|---|
| `project_id` | **Yes** | ID of the parent project |
| `name` | No | Branch name — defaults to branch ID if omitted |
| `parent_id` | No | ID of the parent branch — defaults to the project's default branch |
| `protected` | No | `"yes"` or `"no"` — protect the branch from deletion (paid plans only) |
| `parent_lsn` | No | LSN of the parent to branch from |
| `parent_timestamp` | No | Unix timestamp of the parent to branch from |

### neon_endpoint

Endpoints provide connection strings for a branch. Each branch can have only one `read_write` endpoint.

```hcl
resource "neon_endpoint" "dev_endpoint" {
  project_id = neon_project.my_app_project.id
  branch_id  = neon_branch.dev_branch.id
  type       = "read_write"

  autoscaling_limit_min_cu = 0.25
  autoscaling_limit_max_cu = 0.5
}

output "dev_endpoint_host" {
  value = neon_endpoint.dev_endpoint.host
}
```

Key attributes:

| Attribute | Required | Description |
|---|---|---|
| `project_id` | **Yes** | ID of the parent project |
| `branch_id` | **Yes** | ID of the branch this endpoint connects to |
| `type` | No | `read_write` (default) or `read_only` |
| `autoscaling_limit_min_cu` | No | Minimum compute units |
| `autoscaling_limit_max_cu` | No | Maximum compute units |
| `suspend_timeout_seconds` | No | Inactivity period before suspension (paid plans only) |
| `pooler_enabled` | No | Enable connection pooling |

<Note>
  The `type` attribute is immutable. You cannot change an endpoint from `read_write` to `read_only` or vice versa after creation. Destroy the endpoint and create a new one with the desired type.
</Note>

### neon_role

Roles are Postgres roles scoped to a branch.

```hcl
resource "neon_role" "app_user" {
  project_id = neon_project.my_app_project.id
  branch_id  = neon_branch.dev_branch.id
  name       = "application_user"
}

output "app_user_password" {
  value     = neon_role.app_user.password
  sensitive = true
}
```

Key attributes:

| Attribute | Required | Description |
|---|---|---|
| `project_id` | **Yes** | ID of the parent project |
| `branch_id` | **Yes** | ID of the branch for this role |
| `name` | **Yes** | Name of the Postgres role |
| `password` | Computed | Generated password — sensitive, never shown in plans |

### neon_database

Databases are scoped to a branch and must be owned by an existing role.

```hcl
resource "neon_database" "service_db" {
  project_id = neon_project.my_app_project.id
  branch_id  = neon_branch.dev_branch.id
  name       = "service_specific_database"
  owner_name = neon_role.app_user.name
}
```

Key attributes:

| Attribute | Required | Description |
|---|---|---|
| `project_id` | **Yes** | ID of the parent project |
| `branch_id` | **Yes** | ID of the branch for this database |
| `name` | **Yes** | Name of the database |
| `owner_name` | **Yes** | Name of the role that owns this database |

## Apply your configuration

Once you've defined your resources:

```bash
# Format and validate
terraform fmt
terraform validate

# Preview changes
terraform plan -out=tfplan

# Apply changes
terraform apply tfplan
```

## Import existing resources

If you created Neon resources outside of Terraform — through the console or API — you can bring them under Terraform management.

### Resource ID formats

| Resource | ID format | Example |
|---|---|---|
| `neon_project` | Project ID | `damp-recipe-88779456` |
| `neon_branch` | Branch ID | `br-orange-bonus-a4v00wjl` |
| `neon_endpoint` | Endpoint ID | `ep-blue-cell-a4xzunwf` |
| `neon_role` | `project_id/branch_id/role_name` | `damp-recipe-88779456/br-orange-bonus-a4v00wjl/app_user` |
| `neon_database` | `project_id/branch_id/database_name` | `damp-recipe-88779456/br-orange-bonus-a4v00wjl/mydb` |

Import resources in dependency order: project → branch → endpoint → role → database.

### Method 1: terraform import CLI

```bash
terraform import neon_project.my_app_project "damp-recipe-88779456"
terraform import neon_branch.dev_branch "br-orange-bonus-a4v00wjl"
terraform import neon_endpoint.dev_endpoint "ep-blue-cell-a4xzunwf"
terraform import neon_role.app_user "damp-recipe-88779456/br-orange-bonus-a4v00wjl/application_user"
terraform import neon_database.service_db "damp-recipe-88779456/br-orange-bonus-a4v00wjl/service_db"
```

### Method 2: import blocks (Terraform 1.5.0+)

```hcl
import {
  to = neon_project.my_app_project
  id = "damp-recipe-88779456"
}

resource "neon_project" "my_app_project" {}

import {
  to = neon_branch.dev_branch
  id = "br-orange-bonus-a4v00wjl"
}

resource "neon_branch" "dev_branch" {
  project_id = neon_project.my_app_project.id
  name       = "feature-x-development"
}
```

After importing, run `terraform plan` and update your HCL to match the imported state. Repeat until the plan shows no changes.

## Destroy resources

```bash
terraform destroy
```

Terraform prompts for confirmation before deleting any resources.
