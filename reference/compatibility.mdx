Neon is Postgres. The managed nature of the platform means that a small number of features behave differently or are unavailable compared to a self-hosted installation. This page describes those differences so you can plan your migration or application design accordingly.

## Postgres versions

Neon supports Postgres 14, 15, 16, 17, and 18 (preview). You choose the version when you create a project; you cannot change it afterward. Minor point releases are validated and rolled out by Neon as part of regular platform maintenance.

## Extensions

Neon supports a large and growing set of Postgres extensions. Privilege requirements, local filesystem access, or incompatibility with Autoscaling and Scale to Zero may prevent support for certain extensions. To request an extension, reach out on the [Neon Discord](https://discord.gg/92vNTzKDGp).

<Note>
Neon roles cannot install extensions beyond those supported by the platform, regardless of their privilege level.
</Note>

## Roles and permissions

Neon is a managed service, so you cannot access the host operating system and cannot connect as the Postgres `superuser`. Neon provides a `neon_superuser` role instead.

- Roles created via the Neon Console, CLI, or API are granted membership in `neon_superuser`, which allows creating databases, roles, and reading and writing data across all tables, views, and sequences.
- Roles created with SQL (for example, via `psql` or the SQL Editor) receive the same basic privileges as roles in a standalone Postgres installation. They are **not** granted `neon_superuser` and must be granted permissions explicitly.

<Note>
Postgres parameters are not user-configurable at the instance level. You can configure parameters that have a `user` context for a session, database, or role. Scale plan users who need an instance-level change can contact [Neon Support](/reference/compatibility).
</Note>

### Parameters that scale with compute size

`max_connections`, `maintenance_work_mem`, `shared_buffers`, `max_worker_processes`, and `effective_cache_size` all vary by compute size (measured in [Compute Units](/reference/glossary)).

**`max_connections` formula:**

```text
compute_size = min(max_compute_size, 8 × min_compute_size)
max_connections = max(100, min(4000, floor(compute_size × 419.66)))
```

Examples:

| Configuration | max_connections |
|---|---|
| Fixed 4 CU | 1,678 |
| Autoscaling 0.25–2 CU | 839 |
| Autoscaling 0.25–4 CU | 839 |
| Autoscaling 2–8 CU | 3,357 |

<Tip>
For most applications, use connection pooling, which supports up to 10,000 concurrent connections regardless of compute size. Direct connections are best for `pg_dump`, session-dependent features, or schema migrations.
</Tip>

**`maintenance_work_mem` by compute size:**

| Compute Units (CU) | RAM | maintenance_work_mem |
|---|---|---|
| 0.25 | 1 GB | 64 MB |
| 0.50 | 2 GB | 64 MB |
| 1 | 4 GB | 67 MB |
| 2 | 8 GB | 134 MB |
| 4 | 16 GB | 268 MB |
| 8 | 32 GB | 537 MB |
| 16 | 64 GB | 1074 MB |
| 32 | 128 GB | 2146 MB |
| 56 | 224 GB | 3754 MB |

You can override `maintenance_work_mem` for the current session up to 60% of available RAM:

```sql
SET maintenance_work_mem = '10 GB';
```

**`max_worker_processes` formula:**

```text
max_worker_processes = 12 + floor(2 × max_compute_size)
```

### Configuring parameters for a session, database, or role

You can set any parameter that carries a `user` context. To list them:

```sql
SELECT name FROM pg_settings WHERE context = 'user';
```

Set a parameter for the current session:

```sql
SET maintenance_work_mem = '1 GB';
```

Set a parameter for a database or role:

```sql
ALTER DATABASE neondb SET maintenance_work_mem = '1 GB';
ALTER USER neondb_owner SET maintenance_work_mem = '1 GB';
```

## Unsupported features

### Tablespaces

Neon does not support `CREATE TABLESPACE`. The managed cloud architecture does not allow custom storage locations on the local filesystem. Remove or modify any tablespace references before migrating to Neon.

### `track_commit_timestamp`

The `track_commit_timestamp` parameter is not supported due to platform constraints.

### Superuser access

Direct `superuser` connections are not available. Use the `neon_superuser` role instead.

## Known limitations

### Unlogged tables

Unlogged tables are stored on compute-local storage and are **not persisted** across compute restarts or Scale to Zero suspensions. This differs from standard Postgres, where unlogged tables are only truncated on abnormal process termination. Unlogged tables are also limited by compute local disk space (20 GiB or 15 GiB × maximum compute size, whichever is higher).

<Warning>
Data in unlogged tables is lost whenever the compute restarts or scales to zero. Do not use unlogged tables for data you need to persist.
</Warning>

### Temporary tables

Temporary tables exist only for the duration of a session or transaction and are stored on compute-local storage. They are subject to the same local disk space limits as unlogged tables.

### Session context

Neon automatically closes idle connections after a period of inactivity. When a connection closes, all session-scoped state is lost, including:

- Session-level parameter settings
- Temporary tables
- Prepared statements
- Advisory locks
- `NOTIFY`/`LISTEN` subscriptions

On paid plans you can disable Scale to Zero to keep computes always active. On the Free plan, computes always suspend after 5 minutes of inactivity and Scale to Zero cannot be disabled.

### Postgres statistics

Cumulative statistics collected by the [Postgres statistics system](https://www.postgresql.org/docs/current/monitoring-stats.html) are not saved when a compute is suspended or restarted. Statistics reset on each compute start.

### Database encoding

Neon supports UTF-8 encoding only. You cannot change the encoding or collation of a database after it has been created.

### Collations

Neon uses `C.UTF-8` as the default collation. Standard `libc` locale support is limited compared to a locally installed Postgres instance. Neon provides a full set of predefined ICU locales as an alternative:

```sql
-- List available collations
SELECT * FROM pg_collation;

-- Create a database with an ICU locale
CREATE DATABASE my_arabic_db
  LOCALE_PROVIDER icu
  ICU_LOCALE 'ar-x-icu'
  TEMPLATE template0;

-- Apply a collation to a column
CREATE TABLE my_table (
  id serial PRIMARY KEY,
  content text COLLATE "ru-x-icu"
);
```

### Postgres logs

Postgres logs are available via [Datadog](/reference/compatibility) or [OpenTelemetry](/reference/compatibility) integrations on the Scale plan. For other plans, contact [Neon Support](/reference/compatibility) for specific log information.

### Memory

SQL queries and index builds that generate large volumes of data are bounded by the RAM available on your compute. See [How to size your compute](/features/autoscaling) for guidance on choosing an appropriate compute size.

### Concurrently active computes

The default limit is 20 concurrently active computes per project. If you exceed this limit, additional computes remain suspended until others are stopped. Contact [Neon Support](/reference/compatibility) to request an increase.
