The Data API doesn't have its own permission system. Instead, it acts as a gateway that respects the roles and Row-Level Security (RLS) policies already defined in your Postgres database. This means the same security model you use for direct database access also applies to HTTP queries through the Data API.

Securing your data involves two layers:

1. **Table privileges (GRANT)**: which tables the API role is allowed to access at all.
2. **Row-Level Security (RLS)**: which specific rows within those tables a given user can see or modify.

## How the API chooses a role

When the Data API receives a request, it switches to a specific Postgres role before running the query. The role depends on whether the request includes an `Authorization` header.

### The `authenticated` role

Requests with a valid JWT token run as the `authenticated` role. This is the primary role for your application users. The JWT identifies _who_ the user is via the `sub` claim; the `authenticated` role defines _what_ they're allowed to touch at the table level.

### The `anonymous` role

Requests without a token run as the `anonymous` role. By default, this role has no permissions. If you want to expose public data without requiring users to log in, explicitly grant SELECT to `anonymous`:

```sql
GRANT USAGE ON SCHEMA public TO anonymous;
GRANT SELECT ON TABLE public.products TO anonymous;
```

### Custom roles

If your JWTs include a custom `role` claim (for example, `"role": "admin"`), the API attempts to switch to a Postgres role with that name. The role must exist in your database and have the correct privileges.

## Layer 1: table privileges

Before RLS applies, the Postgres role needs permission to perform the operation on the table. When you enable the Data API in the Neon Console and check **Grant public schema access**, Neon applies these grants automatically:

```sql
-- Allow the role to use the schema
GRANT USAGE ON SCHEMA public TO authenticated;

-- Grant access to all existing tables
GRANT SELECT, UPDATE, INSERT, DELETE ON ALL TABLES IN SCHEMA public TO authenticated;

-- Ensure new tables are automatically accessible
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, UPDATE, INSERT, DELETE ON TABLES TO authenticated;

-- Grant access to sequences (for auto-incrementing IDs)
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO authenticated;
```

If you manage permissions manually, or if you're working with schemas other than `public`, run these commands in the [Neon SQL Editor](https://console.neon.tech) adjusted for your schema and role names.

<Note>
  If you see a "permission denied" error after creating a new table, the `authenticated` role likely doesn't have privileges on it yet. Running the GRANT commands above resolves this.
</Note>

## Layer 2: Row-Level Security

Granting SELECT to the `authenticated` role lets the role read all rows in the table. To restrict which rows each user can access (for example, letting users only see their own posts), you need to enable RLS and create policies.

RLS has three distinct states:

| State | Behavior |
| ----- | -------- |
| RLS disabled | All authenticated users can read all rows |
| RLS enabled, no policies | All access is blocked; no rows are returned |
| RLS enabled with policies | Rows are filtered according to policy rules |

<Warning>
  If RLS is disabled on a table, any authenticated user can read every row. This is true even if you intend to add policies later. Enable RLS and add policies before exposing a table through the Data API.
</Warning>

### The `auth.user_id()` function

The Data API provides `auth.user_id()`, a SQL function that extracts the `sub` claim from the current request's JWT. Use this in your RLS policies to identify the current user.

### Example: per-user access

The following creates a `posts` table where users can only read and modify their own rows:

```sql
-- 1. Create the table with user_id defaulting to the current user
CREATE TABLE posts (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id text DEFAULT (auth.user_id()) NOT NULL,
  content text NOT NULL,
  is_published boolean DEFAULT false,
  created_at timestamp with time zone DEFAULT now() NOT NULL
);

-- 2. Enable RLS
ALTER TABLE posts ENABLE ROW LEVEL SECURITY;

-- 3. Policy: users can read any published post
CREATE POLICY read_published_posts ON posts
  FOR SELECT TO authenticated
  USING (is_published = true);

-- 4. Policy: users have full access to their own posts
CREATE POLICY manage_own_posts ON posts
  FOR ALL TO authenticated
  USING (auth.user_id() = user_id)
  WITH CHECK (auth.user_id() = user_id);
```

### RLS status in the Neon Console

The **Data API** page in the Neon Console shows the RLS status for every table. Tables without RLS enabled display a warning. You can click **Enable RLS** directly in the console to enable it without writing SQL, but you'll still need to create policies to allow access after enabling it.

## Using Drizzle for RLS

If you manage your schema with Drizzle ORM, you can define RLS policies alongside your table schema using `crudPolicy` or `pgPolicy`:

<CodeGroup>

```typescript schema.ts (crudPolicy)
import { sql } from 'drizzle-orm';
import { crudPolicy, authenticatedRole, authUid } from 'drizzle-orm/neon';
import { bigint, boolean, pgTable, text, timestamp } from 'drizzle-orm/pg-core';

export const posts = pgTable(
  'posts',
  {
    id: bigint({ mode: 'number' }).primaryKey(),
    userId: text('user_id')
      .notNull()
      .default(sql`(auth.user_id())`),
    content: text().notNull(),
    isPublished: boolean('is_published').notNull().default(false),
    createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
  },
  (table) => [
    crudPolicy({
      role: authenticatedRole,
      read: sql`is_published OR (auth.user_id() = ${table.userId})`,
      modify: authUid(table.userId),
    }),
  ]
);
```

```typescript schema.ts (pgPolicy)
import { sql } from 'drizzle-orm';
import { authenticatedRole, authUid } from 'drizzle-orm/neon';
import { bigint, boolean, pgPolicy, pgTable, text, timestamp } from 'drizzle-orm/pg-core';

export const posts = pgTable(
  'posts',
  {
    id: bigint({ mode: 'number' }).primaryKey(),
    userId: text('user_id')
      .notNull()
      .default(sql`(auth.user_id())`),
    content: text().notNull(),
    isPublished: boolean('is_published').notNull().default(false),
    createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
  },
  (table) => [
    pgPolicy('read_published_posts', {
      to: authenticatedRole,
      for: 'select',
      using: sql`is_published = true`,
    }),
    pgPolicy('manage_own_posts', {
      to: authenticatedRole,
      for: 'all',
      using: authUid(table.userId),
      withCheck: authUid(table.userId),
    }),
  ]
);
```

</CodeGroup>

`crudPolicy` is a high-level helper that covers most cases in a single declaration. Use `pgPolicy` when you need different logic for different operations.
